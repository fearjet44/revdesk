# T3.6 — Drop a figure anywhere on the page; never open a dropped file

**Task:** T3.6 · **Track:** T3 Editor & figures · **Size:** S · **Branch:** `t3/drop-anywhere` · **Needs:** T3.4 merged (same files; T3 runs serially)
**Read first:** `AGENTS.md`, `docs/handoffs/T3.2-FIGURE-INSERT.md`, then what T3.2 shipped: `src/schema/figure-insert.ts`, the `figureFiles` plugin (`handleDrop` / `handlePaste`) in `src/schema/extensions.ts`, and the `.paper-wrap` block in `src/components/SectionEditor.tsx`.

## Goal

T3.2's drop works only when the file is released over the ProseMirror text. Found while smoking #21: release a PNG from Finder over the left gutter (line numbers), the paper margins, or the title field, and Chrome opens the PNG in a new window. The author expects the whole page to take it.

Two fixes:

1. On an editable working copy, the whole **paper** (`.paper-wrap`: gutter, margins, title, text) takes an image drop and inserts the figure at the nearest block.
2. Anywhere else in the desk, a dropped file does **nothing**. The browser never opens or navigates to a dropped file.

## Done when

- [ ] **Shared drop path** in `src/schema/figure-insert.ts`: one function used by both the ProseMirror `handleDrop` and the paper handler, for example `dropFigure(view, hooks, files, clientX, clientY)`. It takes the first image file, uploads with `uploadOrReport`, and inserts with `insertFigure`. Do not copy the upload/insert code into the component.
- [ ] **Position**: clamp the drop point into the `.ProseMirror` box (x inside its left/right edges, y inside its top/bottom) and use `view.posAtCoords` on the clamped point. If that returns null, insert at the end of the document. Releasing in the gutter beside a paragraph puts the figure at that paragraph, the same as releasing on the paragraph itself.
- [ ] **Paper handler** (`SectionEditor.tsx`, on `.paper-wrap`, only when not `readOnly` and the editor is editable):
  - `dragover` with `Files` in `dataTransfer.types`: `preventDefault()`, `dropEffect = 'copy'`.
  - `drop` with files: if ProseMirror already handled it (`event.defaultPrevented`), do nothing. Otherwise `preventDefault()` and call the shared drop path.
  - Drags with no `Files` (moving text or a block inside the editor) are untouched.
- [ ] **Non-image file** (a `.pdf` or `.docx`) dropped on the paper or the text: show `Only images can be added as figures: PNG, JPEG, GIF, SVG, WebP.` in the editor's existing error banner, and insert nothing. Today `handleDrop` returns false for these; make it handle them.
- [ ] **Drop highlight** (`src/index.css`): while a file is dragged over the paper, show a light dashed outline on `.paper-wrap` (for example a `.is-file-over` class). Clear it on `dragleave` out of the paper, on `drop`, and on `dragend`. A child element's `dragleave` must not clear it, so use a counter or check `relatedTarget`.
- [ ] **Desk-wide guard** (`src/App.tsx`, additive: one `useEffect`, or one small hook in a new T3 file that `App` calls). Add `window` listeners for `dragover` and `drop`. When `dataTransfer.types` includes `Files` and no inner handler has already called `preventDefault()`: on `dragover` call `preventDefault()` and set `dropEffect = 'none'` (the not-allowed cursor); on `drop` call `preventDefault()`. Remove the listeners on unmount.
  - This must not break drops that are meant to work: the paper (above), and any drop zone added later, because an inner handler calls `preventDefault()` first.
  - Read-only views (REVIEW tab, issued sections, managed pages, a change in review) take no drop and open nothing.
- [ ] Paste and the **Figure** button behave as T3.2 left them.
- [ ] `npx tsc -b`, `npm run lint`, `npm run test:md`, `npm run test:review`, `npm run test:slice10` pass.
- [ ] **Manual check with a real Finder drag.** A synthetic `DragEvent` does not reproduce this bug, so the PR must say what a real drag did. Use a scratch library copy (`REVDESK_DATA`) and Vite on a spare port, on a draft working copy in PRINT view. Drop a PNG on:
  - the gutter beside a paragraph: inserted there, caption focused
  - the right margin below the last paragraph: inserted at the end
  - the title field: inserted at the top of the body; the title is unchanged
  - the text, as before: inserted there
  - the toolbar, the sidebar, and the header: nothing happens and no window opens
  - the REVIEW tab and an issued section: nothing happens and no window opens
  - also drop a PDF on the paper: the banner message shows and nothing is inserted
  - also drag a word of text to a new spot in the editor: it still moves
  
  A synthetic-event Playwright script is welcome as `scripts/figures-ui-check.ts`. Do not wire it into `test:md`, and do not add Playwright to `package.json`.

## Out of track (T1, for the planner)

`desk_window` in `src-tauri/src/lib.rs` builds the window with Tauri's native drag-drop handler on (the default). On Windows, HTML5 file drops do not reach the page until the window is built with `.disable_drag_drop_handler()`. Nothing in the desk uses Tauri's drop events. Check the desktop app on macOS too. Report in the PR what you saw if you ran `npm run desktop`; it is not required.
